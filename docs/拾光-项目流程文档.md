## 一、项目背景

### 1.1 产品立意

拾光是一个连接"想通过拍照赚钱的人"与"想找到好摄影师的人"的双边撮合交易 App。

平台一端承接摄影师与创作者的接单变现诉求，一端承接个人与商家对专业拍摄服务的需求，通过作品展示、在线沟通、安全下单、资金托管与信任评价，把"约拍"从分散、无保障的私下交易，变成有撮合、有保障、可沉淀口碑的标准化服务。

产品名"拾光"，取"拾取时光"之意，对应摄影"留住此刻"的本质。

### 1.2 市场痛点

| 对象 | 核心痛点 |
|---|---|
| 摄影师 / 创作者 | 找客户难，接单零散不稳定；作品缺少稳定曝光渠道，获客依赖熟人与私域；交易无保障，常遇爽约、跑单、压价与尾款纠纷；定价缺乏参照，不了解行情 |
| 需求方（个人 / 商家） | 找不到靠谱摄影师，水平与报价不透明；选择成本高，需在多个平台间反复比价；交易无保障，担心付了定金被放鸽子或成品不达标；出问题后缺乏追责手段 |
| 市场整体 | 撮合渠道分散于垂直约拍平台、内容社区私信与泛交易平台，缺少"撮合 + 交易保障 + 信任评价"一体化、具规模的平台 |

### 1.3 项目目标与双边飞轮

对摄影师：提供一站式接单、作品展示、排期管理与收入管理，让摄影师能够持续、稳定、有保障地靠拍摄赚钱。

对需求方：提供搜索筛选、在线沟通、安全下单、资金托管与评价保障，让需求方能够快速、放心地找到合适的摄影师。

对平台：通过撮合服务费与增值服务获利，并驱动飞轮运转：

> 摄影师多 → 供给充足 → 需求方选择多、体验好 → 需求方多 → 订单多 → 摄影师收入高 → 吸引更多摄影师

飞轮的核心约束在于：**供给的质量比数量更早成为瓶颈**。因此 V1.0 把摄影师认证与作品审核放在功能清单的最前端，而非等规模起来再治理。

## 二、研究方法说明

本节说明本项目采用的研究方法与评审机制。

**已采用的方法**：

1. **竞品拆解**：对四类共 15 个相关产品做功能与商业模式层面的对比，识别结构性缺口（见第四章）。
2. **桌面研究**：通过公开渠道了解约拍品类的主流交易方式、常见纠纷类型与用户讨论，用于归纳主流交易方式与纠纷类型的共性模式。
3. **设计推演**：基于撮合交易的通用模型，推导资金托管、状态机与异常分支的设计。
4. **专家评审**：按 Nielsen 十项启发式原则对原型做可用性评审，识别 11 项问题并全部完成修复（见《启发式评估报告》）。

上述方法支撑的是产品结构层面的判断——交易链路、资金路径、状态机与异常分支，这些结论均可追溯到竞品事实与公开讨论记录。定价档位与抽佣比例属于参数化配置，不构成结构性依赖。

## 三、用户画像

### 3.1 需求方：想被记录的人

| 维度 | 描述 |
|---|---|
| 代表人群 | 大学生、职场新人、情侣、宝妈、探店博主 |
| 典型场景 | 写真、毕业照、情侣照、闺蜜照、生日纪念、宠物、探店跟拍、旅拍 |
| 核心诉求 | 找到水平可见、价格透明、不放鸽子的摄影师，且能出好片 |

| 主要顾虑 | 付了定金被放鸽子；成片与样片差距大；价格不透明被临时加价 |

### 3.2 供给侧：想靠拍照赚钱的人

| 维度 | 描述 |
|---|---|
| 代表人群 | 独立摄影师、约拍摄影师、摄影爱好者转兼职、陪拍与跟拍从业者 |
| 典型诉求 | 有稳定客源、作品被看见、接单有保障、收入透明可提现 |

| 画像摘要 | 年龄约 20 至 40 岁；把拍摄作为主业或副业；期望平台带来稳定订单与口碑沉淀 |
| 关键顾虑 | 平台抽佣是否吃掉利润；客户是否会在平台外私下成交；结算是否及时 |

## 四、竞品分析

### 4.1 竞品谱系

| 类别 | 代表产品 | 模式特征 | 主要局限 |
|---|---|---|---|
| 垂直约拍撮合平台 | 咔咔约拍、合拍、麻豆约拍、裹来、去拍拍、拍me | 以撮合为核心，直接连接需求方与摄影师，部分产品已引入保障机制 | 体量分散，多为区域性；供给质量参差；保障机制不统一，多数只覆盖单一环节 |
| 摄影内容社区 | 米拍、蜂鸟摄影 | 内容与社区氛围强，聚集大量摄影师与作品 | 撮合与交易能力弱，社区流量到交易的链路缺失 |
| 泛社交 / 二手交易平台 | 小红书、闲鱼、抖音 | 流量大，用户自发发布约拍需求与作品 | 无撮合结构、无交易保障，多依赖私域成交，纠纷缺乏处理机制 |
| 海外对标 | theCam、CRE8、PicME、Scratch | 已验证"按地理位置找摄影师 + 在线预订"的模式可行 | 本地化成本高，国内供给与支付生态不匹配 |

### 4.2 核心结论与机会点

四类产品的短板呈现明显的互补关系：

- **垂直约拍平台**：有撮合，缺保障。能连上人，但出问题没人兜底。
- **内容社区**：有流量，缺交易。用户看完作品仍需跳转到私信或第三方完成交易。
- **泛交易平台**：有流量，无结构。供需匹配靠搜索与运气，无标准化服务单元。
- **海外产品**：有模式，缺本地化。支付、实名与供给组织方式与国内差异较大。

由此得出差异化机会：

> 不做"又一个作品展示社区"，也不做"又一个信息黄页"，而是做**撮合、保障与信任沉淀一体化的交易基础设施**。

可借鉴的具体做法：

1. 借鉴垂直平台已跑通的保障思路（如爽约金、不满意退款），但将其整合为覆盖交易全链路的四项机制，而非单点功能；
2. 借鉴内容社区以作品建立信任的方式，把作品集作为摄影师主页的第一信息层；
3. 借鉴海外产品的"按位置 + 在线预订"结构，但适配国内支付与实名体系。

## 六、核心业务流程图

### 6.1 下单—履约—结算主流程

| 步骤 | 动作 | 订单状态 |
|---|---|---|
| 1 | 需求方搜索或浏览，查看摄影师与套餐 | —（尚未生成订单） |
| 2 | 选择套餐并约定时间、地点 | 待付款 |
| 3 | 提交订单并支付，款项由平台托管冻结 | 待接单 |
| 4 | 摄影师接单；拒单则自动原路退款 | 待服务 |
| 5 | 按约定时间地点完成拍摄 | 服务中 |
| 6 | 需求方确认验收或发起售后 | 待结算 |
| 7 | 平台扣除撮合服务费后结算给摄影师 | 已结算 |
| 8 | 双方互评，订单完成 | 已完成 |

### 6.2 摄影师入驻认证流程

填写资料 → 实名认证 → 上传资质与作品 → 平台审核 → 通过后开张（驳回则补充材料重提）→ 发布作品与套餐 → 开始接单。

### 6.3 售后与保障流程

需求方申请退款或投诉 → 平台介入 → 判定责任类型（爽约 / 质量不符 / 描述不一致 / 其他）→ 按裁定执行资金处理（全额退回 / 部分结算 / 全额结算）→ 结果留档并计入信用记录。

## 七、产品原型说明

### 7.1 原型概况

原型为单文件 HTML5 应用，使用 CSS3 与原生 JavaScript 手写，无任何外部依赖，可在浏览器中直接打开体验。共 13 屏，覆盖用户端与摄影师端。

### 7.2 页面清单与交互说明

| 序号 | 页面 | 所属端 | 关键交互 |
|---|---|---|---|
| 1 | 首页 | 用户端 | 大图标题区、搜索入口、拍摄类型筛选、作品瀑布流，点击作品进入摄影师主页 |
| 2 | 找摄影师 | 用户端 | 筛选条、摄影师列表，展示认证标识、城市、风格、评分、成交单数与起价 |
| 3 | 摄影师主页 | 用户端 | 作品 / 套餐 / 评价三个 Tab；底部固定价格与"立即预约" |
| 4 | 确认订单 | 用户端 | 套餐信息、时间、地点、联系人、备注；托管说明卡片 |
| 5 | 收银台 | 用户端 | 金额、支付方式选择、担保交易说明 |
| 6 | 我的订单 | 用户端 | 全部 / 待接单 / 待服务 / 已完成四个 Tab，支持取消、联系、评价 |
| 7 | 消息列表 | 用户端 | 会话列表、未读标识 |
| 8 | 会话 | 用户端 | 气泡对话、输入框、可发送消息 |
| 9 | 我的 | 用户端 | 实名标识、订单与收藏统计、功能入口 |
| 10 | 工作台 | 摄影师端 | 今日概览、四项核心指标、待接单卡片（可接单 / 拒单）、待结算提醒 |
| 11 | 作品管理 | 摄影师端 | 九宫格作品、曝光数据、过审状态 |
| 12 | 收入中心 | 摄影师端 | 可提现余额、本月收入、待结算、收支明细、佣金说明 |
| 13 | 数据看板 | 摄影师端 | 四项指标、每日咨询量柱状图、曝光到下单的转化漏斗 |

### 7.3 已实现的业务闭环

原型可完整走通一条交易链路：作品 → 摄影师主页 → 套餐 → 下单 → 托管支付 → 订单回写为"待接单" → 切换至摄影师端接单或拒单 → 查看收入与数据。消息页支持真实发送文本。

筛选、确认与异常分支同样为真实逻辑而非提示文案：首页按拍摄类型筛选作品并回显结果数，搜索页按城市、风格、价格区间、评分筛选摄影师；拒单前弹出二次确认并说明后果；收银台在余额不足时中断支付并给出更换支付方式的恢复路径；各页返回均回退至上一级。

### 7.4 原型边界

平台端管理后台以 PRD 的功能描述与状态机定义为准；支付、退款、结算按状态机在原型内完整流转，覆盖支付成功、余额不足中断与退款回退三类分支。
