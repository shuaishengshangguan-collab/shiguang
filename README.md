# 拾光 ShiGuang · 约拍撮合 App

> 把此刻，拍得值得。

一个面向年轻人的**约拍撮合 App** 产品设计作品，覆盖从竞品分析、用户画像、需求文档、业务流程，到高保真可交互原型、启发式评估与问题修复的完整链路。

🔗 **在线体验**：打开 `index.html`，左侧手机框内即为可点击原型；也可直接打开 `prototype.html` 全屏体验。

---

## 一、项目背景

约拍（付费请人拍照）在年轻人中需求稳定存在，但目前主要靠社交平台私信完成：摄影师在小红书、闲鱼、微博发作品接单，用户在评论区询价，后续的档期确认、报价、定金、修图交付、成片发送全部依赖口头约定。

这种方式对双方都有明显损耗：

| 角色 | 核心痛点 |
| --- | --- |
| 用户 | 无法横向比价；不知道摄影师真实档期；定金打过去没有保障；成片质量和约定不符时无处申诉 |
| 摄影师 | 询价消息大量重复、成单率低；档期靠人工记忆容易撞单；作品散落在多个平台无法沉淀；收入无法统计 |
| 平台视角 | 交易发生在站外，无法形成履约闭环，也无法沉淀评价与信用 |

**产品机会**：把「找摄影师 → 比价 → 下单 → 定金托管 → 履约 → 交付 → 评价」做成站内闭环，用平台担保替代口头信任。

## 四、核心设计：订单状态机

约拍的本质是一次**带资金托管的服务交易**，所以订单模型是整个产品的骨架。

```
正常流转
待付款 ─支付→ 待接单 ─接单→ 待服务 ─开拍→ 服务中 ─拍摄完成→ 待结算 ─确认验收→ 已结算 → 已完成

异常分支
待付款 ─超时未支付 / 用户取消→ 已取消
待接单 ─摄影师拒单 / 超时未接→ 退款中 → 已退款
待结算 ─用户发起售后→ 售后中 → 平台裁定 → 已结算 或 已退款
待结算 ─72 小时未操作→ 系统自动确认 → 已完成
```

关键的设计取舍：

1. **全款托管、验收后放款**：用户支付后款项进入平台托管，摄影师完成交付且用户确认后才结算，解决"付了钱拿不到片"和"拍了照收不到钱"的双向不信任。不采用定金模式，是因为定金只能约束签约，约束不了交付质量。
2. **接单前可全额退**：摄影师未接单时用户取消全额退款，把决策成本降到最低，鼓励下单。
3. **72 小时自动确认**：避免用户长期不验收导致摄影师回款被卡，同时给出"申请修改"的缓冲入口。
4. **拒单与超时同构**：摄影师拒单和超时未接单走同一退款路径，减少一套状态分支。

## 五、原型说明

`prototype.html` 是一个**单文件**高保真原型：

- 纯 HTML + CSS + 原生 JS，**无任何外部依赖**（无 CDN、无图片文件、无字体包）
- 所有图片位由运行时生成的 SVG 渐变填充，因此断网也能完整显示
- 内置极简路由（`go(view, param)`），13 个页面共用一套壳层
- 建议用手机尺寸查看：浏览器开发者工具切到 iPhone 14（390×844）体验最佳

**页面清单**

| 端 | 页面 |
| --- | --- |
| 用户端（9） | 首页、找摄影师、摄影师主页、确认订单、收银台、我的订单、消息、会话、我的 |
| 摄影师端（4） | 工作台、作品管理、收入中心、数据看板 |

**体验路径建议**

1. 首页 → 点任意摄影师 → 摄影师主页 → 立即预约 → 确认订单 → 收银台 → 支付 → 我的订单
2. 「我的」页底部可切换到摄影师端，体验接单 / 拒单与收入中心
3. 消息 → 任意会话，查看订单卡片在对话中的锚定方式
